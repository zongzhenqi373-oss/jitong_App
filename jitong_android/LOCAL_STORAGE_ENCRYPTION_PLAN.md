# 即通 Android 本地存储安全加密实施方案

## 1. 目标与范围

本方案只处理即通 Android 客户端的本地存储安全，不改动 IM 通信协议、服务端数据库和消息传输流程。

必须保护的数据包括：

| 数据 | 当前存储位置 | 目标保护方式 |
|---|---|---|
| 文本消息、会话、好友资料、FTS索引 | Room：`jitong.db` | SQLCipher整库加密 |
| 图片消息 | `filesDir/img/` | AES-256-GCM文件加密 |
| 接收的文件 | `filesDir/file/` | AES-256-GCM分块加密 |
| 待发送文件副本 | `filesDir/file/outgoing/` | AES-256-GCM分块加密 |
| 下载中的临时分片 | `.part`文件 | 到达后直接加密落盘 |
| 登录凭证 | MMKV | 不再保存明文密码；敏感凭证由Keystore加密 |

安全目标是：攻击者即使复制了应用私有目录，也不能直接读取数据库、图片、文件或登录凭证。

本方案不试图防御已经控制App进程的实时Hook、Root后内存读取或用户主动导出给第三方应用后的明文副本。

## 2. 总体设计

采用一套简单的两级密钥结构：

| 密钥 | 产生方式 | 用途 | 保存方式 |
|---|---|---|---|
| Keystore包装密钥 | Android Keystore生成AES-256密钥 | 包装账号数据密钥 | 不可导出，保存在系统Keystore |
| 账号数据密钥 | `SecureRandom`生成32字节 | SQLCipher开库，并派生媒体密钥 | AES-GCM包装后保存在应用私有目录 |

每个登录账号在本机拥有独立的数据密钥、数据库和媒体目录，避免多账号共用同一把密钥。

建议目录布局：

| 内容 | 路径示例 |
|---|---|
| 加密数据库 | `databases/jitong_10001.db` |
| 数据密钥包装信息 | `files/secure/10001/db_key.bin` |
| 加密图片 | `files/secure/10001/img/<msgId>.jtm` |
| 加密接收文件 | `files/secure/10001/file/<fileId>.jtf` |
| 加密待发送副本 | `files/secure/10001/outgoing/<msgId>.jtf` |
| 加密下载临时文件 | `files/secure/10001/tmp/<fileId>.part` |

## 3. Android Keystore设计

### 3.1 包装密钥

Keystore别名固定为应用级版本化名称，例如 `jitong.local.wrap.v1`。一台设备只需要一把包装密钥，不需要为每个消息或文件创建Keystore条目。

密钥参数：

| 参数 | 选择 |
|---|---|
| 算法 | AES |
| 密钥长度 | 256位 |
| 模式 | GCM |
| Padding | NoPadding |
| 用途 | Encrypt、Decrypt |
| 随机数 | 系统安全随机数 |
| 导出 | 禁止，Keystore密钥不可导出 |

当前即通项目不强制每次打开App进行生物识别，避免登录和弱网自动重连流程变复杂。后续如果增加“隐私锁”，再为包装密钥启用用户认证要求。

StrongBox可作为能力增强：设备支持时优先使用，不支持时回退到TEE或系统Keystore，不能因为设备没有StrongBox导致应用无法登录。

### 3.2 账号数据密钥

用户第一次在当前设备登录成功后：

1. 生成32字节随机账号数据密钥。
2. 使用Keystore包装密钥通过AES-GCM加密账号数据密钥。
3. 将格式版本、用户ID、IV和密文写入账号密钥文件。
4. 原始账号数据密钥仅在需要打开数据库和处理媒体文件时保留在内存中。

后续登录：

1. 服务端登录成功并返回用户ID。
2. 根据用户ID读取账号密钥文件。
3. 使用Keystore解包账号数据密钥。
4. 使用该密钥打开账号独立的SQLCipher数据库。

主动退出、被踢下线或切换账号时：

1. 关闭Room数据库。
2. 清空`ChatStore`和数据库单例引用。
3. 尽可能覆盖内存中的密钥字节。
4. 保留本地密文和包装后的数据密钥，供下次登录使用。

## 4. Room数据库加密

### 4.1 技术选型

使用新版SQLCipher Android绑定，通过`SupportOpenHelperFactory`接入现有Room。

数据库继续保留当前实体、DAO、FTS4和迁移逻辑，只更换底层SQLite OpenHelper。

### 4.2 每账号独立数据库

现有固定数据库名`jitong.db`改为根据登录用户生成，例如`jitong_<userId>.db`。

虽然每个数据库只属于一个账号，现有`ownerId`字段仍然保留，用于业务查询和防御性校验，不在本次改造中大规模修改表结构。

### 4.3 初始化时序

当前项目在`MainActivity`启动后立即构造`ChatStore`并打开Room，这不适用于加密数据库。

改造后的时序：

1. `MainActivity`只向`MainViewModel`注入Application Context、ContentResolver等无密钥依赖对象。
2. 登录页面不创建`ChatStore`，也不打开数据库。
3. 收到服务端`LOGIN_SUCCESS`后，根据`userId`获取账号数据密钥。
4. 创建`AppDatabase(context, userId, dbKey)`。
5. 创建`ChatStore(context, database, mediaCrypto)`。
6. 执行`hydrate(userId)`加载本地消息。
7. 发起服务端会话漫游，补齐本地缺失数据。

### 4.4 数据库关闭

`AppDatabase`新增明确的`closeCurrent()`能力。以下情况必须关闭：

- 用户主动退出登录；
- 服务端踢下线；
- 切换账号；
- 数据密钥解包失败；
- 数据库判定损坏并准备重建。

TCP临时断线和自动重连期间不关闭数据库，避免反复开库和破坏当前聊天状态。

## 5. 图片加密

当前图片消息由`ChatStore.writeImageFile()`直接写成PNG/JPG明文文件，必须改为加密文件。

### 5.1 图片密钥

从账号数据密钥通过HKDF-SHA256派生图片主密钥，派生上下文固定包含：

- 应用标识；
- 格式版本；
- 用户ID；
- `media-image`用途标识。

每张图片使用独立随机12字节IV，通过AES-256-GCM加密。

### 5.2 图片文件格式

每个`.jtm`文件包含：

| 字段 | 说明 |
|---|---|
| Magic | 固定文件标识，用于拒绝错误格式 |
| Version | 加密格式版本 |
| IV | AES-GCM随机IV |
| MIME | 原图片类型，如PNG/JPEG |
| OriginalSize | 原始长度 |
| Ciphertext | 图片密文及GCM认证标签 |

用户ID、消息ID和格式版本作为GCM关联数据参与认证，防止攻击者把一个账号或消息的密文替换到另一条消息下。

### 5.3 显示流程

聊天页面需要显示图片时：

1. 从加密文件读取数据。
2. 验证文件头和版本。
3. 使用图片密钥和关联数据执行AES-GCM解密。
4. 将解密结果直接交给`BitmapFactory`。
5. 不在磁盘上产生临时明文图片。

当前`ChatMessage.imageBytes`可以暂时保留，因此对UI层改动较小。

## 6. 文件加密

文件可能达到100MB，不能整文件读入内存，也不适合对整个文件一次性执行AES-GCM。

### 6.1 分块格式

继续沿用项目当前256KB业务分片，每个本地加密块独立使用AES-256-GCM。

每块包含：

| 字段 | 说明 |
|---|---|
| ChunkIndex | 分片编号 |
| PlainLength | 原始分片长度 |
| IV | 当前块随机IV |
| CipherLength | 密文长度 |
| Ciphertext | 分片密文及认证标签 |

GCM关联数据包含用户ID、文件ID、分片编号、文件总大小和格式版本，防止分片调换、重复和跨文件替换。

### 6.2 发送文件

当前项目会先把SAF文件复制到`filesDir/file/outgoing`。改造后流程为：

1. 用户从系统文件选择器选择文件。
2. 从ContentResolver按流读取原文件。
3. 一边读取一边计算原文件SHA-256。
4. 每256KB立即加密并写入本地`.jtf`文件。
5. 不再在应用私有目录留下明文发送副本。
6. 上传时逐块解密到内存，并将明文分片交给现有`FileChunkRq`发送。
7. 每次内存中只存在一个分片，发送后覆盖或释放缓冲区。

文件重试仍然复用本地加密副本和原`msgId`，不依赖外部文件是否仍可访问。

### 6.3 接收文件

下载时流程为：

1. 网络收到一个明文业务分片。
2. 验证`fileId`和`chunkIndex`。
3. 立即使用AES-GCM加密该分片。
4. 写入本地加密`.part`文件。
5. 更新数据库中的已接收分片水位线。
6. 下载完成后验证原文件SHA-256。
7. 将加密`.part`原子重命名为正式`.jtf`文件。

磁盘上不保存完整明文文件。

### 6.4 打开和导出文件

第三方应用无法直接打开即通私有加密格式。用户点击“打开”时：

1. 解密到`cacheDir/share/<randomName>`临时文件。
2. 使用FileProvider生成短期`content://`地址。
3. 只授予目标Intent临时读取权限。
4. 设置定时清理，并在App下次启动时清理遗留临时明文。

用户导出给第三方应用后产生的副本不再受即通控制，这是产品边界，需要在隐私说明中明确。

## 7. 登录凭证保护

当前`Prefs.pass`将明文密码写入MMKV，必须删除该行为。

本次改造建议：

- MMKV只保存非敏感的手机号和“记住账号”开关；
- 不再回填和保存明文密码；
- 当前重连阶段可暂时只在进程内保存`lastHash`；
- 进程被杀后重新输入密码登录；
- 后续服务端支持Refresh Token后，再使用独立Keystore AES-GCM密钥加密Token。

数据库密钥包装文件不能存入MMKV，以独立二进制文件保存并使用原子写入。

## 8. 旧数据迁移

当前`jitong.db`及图片、文件都是明文。由于即通已经支持服务端消息漫游，本次不做复杂的原地加密迁移。

升级后的处理策略：

1. 登录成功后检查旧版固定数据库`jitong.db`。
2. 如果存在，关闭所有旧数据库引用。
3. 删除主库、`-wal`和`-shm`文件。
4. 删除旧版明文`img`、`file`和`outgoing`目录。
5. 创建账号独立的加密数据库和媒体目录。
6. 通过服务端漫游重新恢复消息。
7. 文件卡片可以恢复，但实际文件需要用户重新下载。

这样可以保证升级后不继续残留历史明文文件。

## 9. 异常恢复

| 异常 | 处理方式 |
|---|---|
| Keystore别名不存在 | 删除本地加密缓存，生成新密钥后漫游恢复 |
| AES-GCM认证失败 | 视为密钥错误、文件损坏或被篡改，不返回不可信明文 |
| SQLCipher开库失败 | 关闭实例，删除本账号数据库及WAL/SHM后重建 |
| 图片文件损坏 | 删除单张图片，重新从服务端获取；无法获取则显示占位 |
| 文件分片损坏 | 删除或回退损坏分片，从服务端断点重下 |
| App重装/清除数据 | 本地密钥和缓存全部丢失，重新登录并漫游恢复 |
| 设备不支持StrongBox | 自动回退到普通Android Keystore |
| 存储空间不足 | 暂停写入，不删除已验证的加密分片 |

本地数据库和媒体是服务端数据的缓存，因此密钥失效时优先安全重建，不尝试绕过认证恢复明文。

## 11. 分阶段实施

### 第一阶段：数据库和凭证

1. 引入SQLCipher。
2. 实现`DbKeyManager`。
3. 改为每账号独立数据库。
4. 登录成功后开库，退出时关库。
5. 删除MMKV明文密码。
6. 清理旧明文数据库并通过漫游恢复。

验收标准：复制数据库文件后，普通SQLite工具无法读取；错误密钥无法开库；不同账号不能互相打开数据库。

### 第二阶段：图片

1. 新增`EncryptedImageStore`。
2. 新图片全部加密落盘。
3. 聊天界面按需解密显示。
4. 清理旧明文图片目录。

验收标准：磁盘中不能直接识别PNG/JPEG魔数；篡改一个字节后必须解密失败。

### 第三阶段：文件

1. 新增分块加密文件格式。
2. 发送副本改为边复制边加密。
3. 下载分片改为边接收边加密。
4. 打开文件时通过临时明文和FileProvider共享。
5. 增加临时文件清理任务。

验收标准：磁盘中不存在完整明文发送或接收文件；100MB文件不会整体进入内存；断点续传和重试保持有效。

## 12. 测试清单

### 数据库测试

- 正确密钥可以打开数据库；
- 错误密钥无法打开；
- 主库、WAL和SHM中搜索不到消息正文；
- 两个账号使用不同数据库和不同账号数据密钥；
- 主动退出后数据库实例已关闭；
- 断线重连期间数据库不会重复创建；
- App重装后安全重建并完成漫游。

### 图片测试

- PNG、JPEG收发和重启后显示正常；
- 加密文件没有原图片魔数；
- 文件头、IV、密文任意一处被篡改均不能显示；
- 大图解密不会阻塞主线程；
- 图片文件与账号、消息ID绑定。

### 文件测试

- 空文件、末块不足256KB、100MB上限正常；
- 上传、下载、暂停、续传、重试正常；
- 本地只存在加密文件；
- 分片调换、重复、篡改能被识别；
- 第三方打开使用临时授权；
- App重启后能清理遗留临时明文；
- 取消任务后文件流和后台协程正确结束。

### 凭证测试

- MMKV中不存在明文密码和固定密码摘要；
- 日志不输出密码、Token、账号数据密钥和媒体密钥；
- Keystore密钥删除后旧本地数据无法解密；
- 备份文件不包含可恢复的本地密钥材料。

## 13. 最终验收标准

本地存储加密改造完成后，应满足：

1. Room数据库、WAL、SHM均由SQLCipher保护。
2. 图片、文件、待发送副本和下载临时分片均以密文落盘。
3. 每个账号使用独立数据库、独立账号数据密钥和独立媒体目录。
4. 账号数据密钥只以Android Keystore包装后的形式持久化。
5. 用户密码不再以明文或固定摘要持久化。
6. 登录成功后才打开数据库，退出或切换账号时关闭数据库。
7. 本地密钥损坏或丢失时安全清理，并通过服务端漫游恢复。
8. 任何AES-GCM认证失败都不得降级为明文读取。
9. 打开第三方文件时产生的临时明文可追踪、可清理、权限受限。
10. 不影响现有文本、图片、文件、离线补发、消息漫游和断点续传业务。
